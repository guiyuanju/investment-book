# 章节编写 → 审阅 → 修复 流程

本书的读者、写作原则、章节结构见 `docs/guide.md`，目录见 `docs/outline.md`。每次开始前先读这两个文件，以及与目标章节相邻的已完成章节，保持风格和交叉引用一致。

参数：用户指定的部分或章节（例如“第二部分”、“第 6–9 章”）。

## 第 1 步：写作

对每一章：

1. **确认范围**：从 `docs/outline.md` 读取本章的小节列表和计划案例；占位文件是 `docs/partXX/chYY.md`（含“本章正文撰写中”）。如果需要修改目录（增删小节），先改 `outline.md`，再运行 `npm run sync`（不会覆盖已写好的章节）。
2. **按固定结构写**（参照 `docs/part01/ch01.md`）：
   - 标题行 `# 第N章 标题 难度标记`，下一行 `> 第X部分 · 部分名`
   - `::: tip 学习目标`
   - 按目录的小节逐节写：概念 → 数值例子 → 真实案例
   - `## 常见误区`（表格）→ `## 本章小结` → `## 思考与练习` + `::: details 参考思路`
3. **写作要求**：
   - 读者是在日本生活、读中文的初学者；日中美三个市场都要覆盖，**日本的例子和制度优先**。
   - 术语首次出现给出 英文／日文，例如“久期（Duration／デュレーション）”。
   - 每个数据注明时间、来源和口径（名义/实际、是否含股息、价格指数/总回报）。
   - 区分事实与观点；有争议的问题列出不同观点。
   - 讲成功案例时提醒幸存者偏差。
   - 案例要说明“发生了什么 → 为什么 → 教训”，并和本章概念明确挂钩。
   - 用“期望”“通常”“大致”等措辞准确表达不确定性，不写“必然”“一定”，除非数学上成立（例如赌博的负期望值）。
   - 只引用目录中存在的章节号；不要把后续章节的专题内容提前展开，点到为止并注明“第 N 章”。
   - 公式用 `$...$` / `$$...$$`（已启用 MathJax）。
4. **事实核查（写的同时做）**：
   - 所有计算都用 `python3` 重算一遍，不要心算。
   - 2024 年以后的数据、制度、利率、法规，以及任何不确定的数字，**必须用 WebSearch 核实**，不能凭记忆写。今天的日期以系统提示为准。
   - 无法核实的说法：删掉，或者软化为不含具体数字的表述，或者注明“据报道”。
5. **构建检查**：`npm run build` 必须成功（会检查死链）。

## 第 2 步：审阅（使用 subagent）

写完一批章节后，**每章启动一个 general-purpose subagent 并行审阅**（`run_in_background` 默认即可），prompt 使用 [reviewer-prompt.md](reviewer-prompt.md)，把 `{{CHAPTER_PATH}}` 替换为章节路径，`{{FOCUS}}` 替换为本章需要重点核查的事实清单（日期、数字、人名、法规、2024 年以后的数据）。

要求 subagent **只审阅，不修改文件**。等全部返回后再汇总，不要猜测未返回的结果。

## 第 3 步：向用户汇报

汇总成：
- 评分表（章节 × 正确性/完备性/深度/启发性）
- 共性问题（跨章节反复出现的问题）
- “必须修改”清单（事实错误、过时信息、概念漏洞），按章节列出
- “建议修改”和“可选增强”的要点
- 哪些新事实超出了自己的知识范围、需要在修复时核实

然后询问用户采纳哪些级别（默认推荐：必须修改 + 建议修改）。

## 第 4 步：修复

1. **独立核实审阅者提供的新事实**：对审阅者给出的、尤其是 2024 年以后的数据，自己再用 WebSearch/WebFetch 查证；搜索结果相互矛盾时，只写能确认的部分。
2. 用 Edit 逐条修改；新增的数字全部用 `python3` 重算。
3. 修改后同步检查：本章小结、常见误区、练习答案是否与正文一致；目录 `outline.md` 的小节标题是否需要同步。
4. `npm run build` 通过。
5. 向用户汇报改了什么、哪些没能核实，并附上来源链接。

## 第 5 步：发布

用户确认后提交并推送（GitHub Actions 会自动部署到 GitHub Pages）：

```bash
git add -A && git commit -m "Write part N: chapters X–Y" && git push
```

推送后可以用 `gh run watch` 确认部署成功。
